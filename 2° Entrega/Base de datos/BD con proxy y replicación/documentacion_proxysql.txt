=====================================================================
DOCUMENTACION: REPLICACION MYSQL + BALANCEO DE CARGA CON PROXYSQL
Proyecto Translogistica
=====================================================================

1. OBJETIVO
---------------------------------------------------------------------
Tener una base de datos MySQL con replicacion (un servidor primario y
uno secundario) y un proxy (ProxySQL) que reparta las consultas:
  - Las escrituras (INSERT, UPDATE, DELETE, CREATE) van al primario.
  - Las lecturas (SELECT) van al secundario.
La aplicacion (Laravel) se conecta solo al proxy.

Todo corre en contenedores Docker, definidos en un docker-compose.


2. ARQUITECTURA
---------------------------------------------------------------------
  Laravel / MySQL Workbench
            |
            v
     ProxySQL (puerto 6033)
        |            |
  escrituras      lecturas
        |            |
        v            v
  Translogistica_  Translogistica_
  primario         secundario
  (hostgroup 10)   (hostgroup 20)
        |            ^
        +-replicacion+
            (GTID)

Puertos publicados en el equipo (host):
  - 3307 -> MySQL primario (conexion directa, para administracion)
  - 3308 -> MySQL secundario (conexion directa, solo lectura)
  - 6033 -> ProxySQL, trafico de clientes (aqui se conecta la app)
  - 6032 -> ProxySQL, consola de administracion

Importante: dentro de la red de Docker, los contenedores se ven por
el NOMBRE del servicio (Translogistica_primario, etc.) y siempre por
el puerto 3306, no por los puertos 3307/3308.


3. DOCKER-COMPOSE
---------------------------------------------------------------------
Servicios definidos:

a) Translogistica_primario
   - Imagen: mysql:8.0.30-debian
   - server-id=1, binlog activado, GTID activado, formato ROW.
   - Base inicial: Replicacion_Translogistica
   - Puerto 3307 -> 3306, volumen datos_primario.

b) Translogistica_secundario
   - Imagen: mysql:8.0.30-debian
   - server-id=2, relay-log, GTID activado, read-only=ON.
   - Puerto 3308 -> 3306, volumen datos_secundario.

c) proxysql
   - Imagen: proxysql/proxysql:2.7.3
   - Puertos 6033 (clientes) y 6032 (administracion).
   - Volumen proxysql (guarda la configuracion del proxy).
   - restart: always

Red: reddecontenedores (bridge), compartida por los tres servicios.

Levantar todo:
  docker compose up -d


4. REPLICACION PRIMARIO -> SECUNDARIO
---------------------------------------------------------------------
Se configuro con GTID y auto-posicion.

4.1 En el PRIMARIO se crea el usuario de replicacion:

  CREATE USER 'repl'@'%' IDENTIFIED BY 'repl_pass';
  GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

4.2 En el SECUNDARIO se apunta al primario y se inicia la replica:

  CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='Translogistica_primario',
    SOURCE_USER='repl',
    SOURCE_PASSWORD='repl_pass',
    SOURCE_AUTO_POSITION=1,
    GET_SOURCE_PUBLIC_KEY=1;
  START REPLICA;

4.3 Verificacion (en el secundario):

  SHOW REPLICA STATUS\G

Deben estar en "Yes":
  - Replica_IO_Running
  - Replica_SQL_Running


5. USUARIOS
---------------------------------------------------------------------
Usuarios de MySQL (se crean en el PRIMARIO y se replican solos al
secundario):

  Usuario    Contrasena      Para que sirve
  ---------  --------------  ------------------------------------------
  root       root            Administracion de MySQL (solo uso interno)
  repl       repl_pass       Replicacion entre primario y secundario
  monitor    monitor_pass    ProxySQL lo usa para vigilar los servidores
  laravel    laravel_pass    Usuario de la aplicacion (via el proxy)

Creacion de monitor y laravel (en el primario):

  CREATE USER 'monitor'@'%' IDENTIFIED BY 'monitor_pass';
  GRANT USAGE, REPLICATION CLIENT ON *.* TO 'monitor'@'%';

  CREATE USER 'laravel'@'%' IDENTIFIED BY 'laravel_pass';
  GRANT ALL ON Replicacion_Translogistica.* TO 'laravel'@'%';
  GRANT ALL ON translogistica.* TO 'laravel'@'%';

Usuario de administracion de ProxySQL (NO es un usuario de la base):
  admin / admin  -> solo entra desde dentro del contenedor, puerto 6032.

NOTA: son contrasenas de ejemplo para el entorno de pruebas. En un
entorno real deben cambiarse.


6. CONFIGURACION DE PROXYSQL
---------------------------------------------------------------------
6.1 Entrar a la consola de administracion (PowerShell):

  docker exec -it proxysql mysql -h 127.0.0.1 -P 6032 -u admin -padmin

(Se escribe con espacios entre -h, -P, -u y su valor porque PowerShell
cortaba "-h127.0.0.1" y daba el error "Can't connect to server on
'127'".)

6.2 Usuario de monitoreo:

  UPDATE global_variables SET variable_value='monitor'
    WHERE variable_name='mysql-monitor_username';
  UPDATE global_variables SET variable_value='monitor_pass'
    WHERE variable_name='mysql-monitor_password';
  LOAD MYSQL VARIABLES TO RUNTIME;
  SAVE MYSQL VARIABLES TO DISK;

6.3 Servidores backend y grupos:

  INSERT INTO mysql_servers (hostgroup_id, hostname, port)
    VALUES (10, 'Translogistica_primario', 3306);
  INSERT INTO mysql_servers (hostgroup_id, hostname, port)
    VALUES (20, 'Translogistica_secundario', 3306);
  INSERT INTO mysql_replication_hostgroups
    (writer_hostgroup, reader_hostgroup, comment)
    VALUES (10, 20, 'replicacion');
  LOAD MYSQL SERVERS TO RUNTIME;
  SAVE MYSQL SERVERS TO DISK;

  - Hostgroup 10 = escritura (primario).
  - Hostgroup 20 = lectura (secundario).
  - ProxySQL decide quien es escritor y quien lector segun el valor
    read_only de cada servidor.

6.4 Usuario de la aplicacion y reglas de enrutamiento:

  INSERT INTO mysql_users (username, password, default_hostgroup)
    VALUES ('laravel', 'laravel_pass', 10);

  INSERT INTO mysql_query_rules
    (rule_id, active, match_digest, destination_hostgroup, apply)
    VALUES (1, 1, '^SELECT.*FOR UPDATE', 10, 1);
  INSERT INTO mysql_query_rules
    (rule_id, active, match_digest, destination_hostgroup, apply)
    VALUES (2, 1, '^SELECT', 20, 1);

  LOAD MYSQL USERS TO RUNTIME;
  SAVE MYSQL USERS TO DISK;
  LOAD MYSQL QUERY RULES TO RUNTIME;
  SAVE MYSQL QUERY RULES TO DISK;

Reglas:
  - Regla 1: SELECT ... FOR UPDATE -> primario.
  - Regla 2: cualquier otro SELECT -> secundario.
  - Todo lo demas (INSERT, UPDATE, DELETE, DDL) -> primario, porque es
    el grupo por defecto del usuario.

6.5 Base de datos por defecto del usuario:

  UPDATE mysql_users SET default_schema='translogistica'
    WHERE username='laravel';
  LOAD MYSQL USERS TO RUNTIME;
  SAVE MYSQL USERS TO DISK;

Sin esto, la sesion abria en information_schema y daba errores de
acceso denegado.

6.6 Verificacion de los servidores:

  SELECT hostgroup_id, hostname, status FROM runtime_mysql_servers;

Resultado esperado: los dos servidores en estado ONLINE.


7. CONEXION DESDE MYSQL WORKBENCH
---------------------------------------------------------------------
  Hostname:  127.0.0.1
  Puerto:    6033   (NO usar 6032)
  Usuario:   laravel
  Password:  laravel_pass

Problema inicial: Workbench mostraba "Unable to connect to
127.0.0.1:3306" porque se estaba usando el puerto 6032 y el usuario
admin, que corresponden a la consola de administracion de ProxySQL y
no a la base de datos.


8. CONEXION DESDE LARAVEL (.env)
---------------------------------------------------------------------
  DB_HOST=127.0.0.1
  DB_PORT=6033
  DB_DATABASE=translogistica
  DB_USERNAME=laravel
  DB_PASSWORD=laravel_pass

Si Laravel corre dentro de un contenedor de la misma red, usar
DB_HOST=proxysql.


9. PRUEBAS REALIZADAS
---------------------------------------------------------------------
a) Lectura: SELECT @@hostname
   -> devolvio Translogistica_secundario (lectura va al secundario).

b) Lectura con bloqueo: SELECT @@hostname FOR UPDATE
   -> va al primario (regla 1).

c) Escritura:
     USE Replicacion_Translogistica;
     CREATE TABLE IF NOT EXISTS prueba_proxy
       (id INT PRIMARY KEY AUTO_INCREMENT, texto VARCHAR(50));
     INSERT INTO prueba_proxy (texto) VALUES ('hola desde proxysql');
     SELECT * FROM prueba_proxy;
   -> el CREATE y el INSERT se ejecutaron (solo el primario acepta
      escrituras) y el SELECT mostro la fila (replicada al secundario).

d) Base real: tras dar permisos sobre translogistica al usuario
   laravel, la base y su tabla clientes aparecieron en el proxy.

La tabla prueba_proxy de la base Replicacion_Translogistica se dejo
creada como evidencia de la prueba.


10. COMO VER A QUE SERVIDOR FUE CADA CONSULTA
---------------------------------------------------------------------
En la consola de administracion de ProxySQL:

  -- Consultas y el hostgroup al que fueron
  SELECT hostgroup, username, count_star, digest_text
  FROM stats_mysql_query_digest
  ORDER BY last_seen DESC LIMIT 20;

  -- Total de consultas por servidor
  SELECT hostgroup, srv_host, Queries
  FROM stats_mysql_connection_pool;

hostgroup 10 = primario, hostgroup 20 = secundario.

Desde Workbench, para lecturas:
  SELECT @@hostname, texto FROM prueba_proxy;


11. PROBLEMAS ENCONTRADOS Y SOLUCIONES
---------------------------------------------------------------------
1) "Unable to connect to 127.0.0.1:3306" en Workbench
   Causa: puerto 6032 y usuario admin (consola de ProxySQL).
   Solucion: usar el puerto 6033 y un usuario de aplicacion.

2) ProxySQL sin servidores ni usuarios
   Causa: arranca vacio, no se monto ningun proxysql.cnf.
   Solucion: cargar mysql_servers, mysql_users y reglas desde la
   consola de administracion (pasos 6.2 a 6.5).

3) "Can't connect to server on '127'" en PowerShell
   Causa: PowerShell cortaba -h127.0.0.1 en el primer punto.
   Solucion: escribir -h 127.0.0.1 -P 6032 -u admin -padmin.

4) "Access denied for user 'laravel' to database 'information_schema'"
   Causa: la sesion no tenia base por defecto.
   Solucion: USE <base> o default_schema en mysql_users (paso 6.5).

5) La base translogistica no aparecia
   Causa: el usuario laravel solo tenia permisos sobre
   Replicacion_Translogistica.
   Solucion: GRANT ALL ON translogistica.* TO 'laravel'@'%';

6) Error de sintaxis al poner @@hostname dentro de un CREATE TABLE
   Causa: @@hostname es una variable para usar en SELECT, no va dentro
   de sentencias DDL.


12. NOTAS FINALES
---------------------------------------------------------------------
- Con las reglas actuales, una lectura inmediatamente posterior a una
  escritura podria devolver datos viejos si el secundario todavia no
  replico (retraso de replicacion).
- El volumen "proxysql" guarda la configuracion, por lo que no hay que
  repetir el paso 6 al reiniciar los contenedores.
- Cambiar todas las contrasenas de ejemplo antes de usar en produccion.
